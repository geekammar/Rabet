# S1.2 — Tenant ownership expansion

**Scope:** additive schema preparation only. The application remains single-store
until a separately approved backfill (not executed here) and a later enforcement
phase. No additional store, merchant or membership is activated by this change.

## 1. Baseline

- Repository baseline: `main` at the merge of S1.1
  (`0005_tenant_identity_foundation` applied by the reviewed chain).
- S1.1 identity tables: `store`, `app_user`, `store_membership`.
- Existing application tables remain the operational schema. Migration `0006`
  only adds nullable `store_id` columns, foreign keys and non-unique indexes.

## 2. Ownership matrix

`PK` is the primary key, `Parent` is the row that determines ownership when no
direct column is added.

| Table | PK | Parent ownership | Direct `store_id` | Existing unique constraints | Existing FKs | Parent-derived sufficient | Future composite FK |
| --- | --- | --- | --- | --- | --- | --- | --- |
| `store` | `id` | root tenant | n/a (is the store) | `store_slug_unique` | none | n/a | none |
| `app_user` | `id` | global identity | no | `app_user_email_lower_unique` | none | yes; a user may join many stores | none |
| `store_membership` | `id` | `store`, `app_user` | already `store_id` | `store_membership_store_user_unique` | store, user | no; explicit link | none |

### 2.1 Why these eight roots get a direct column

`bot_setting`, `category`, `product`, `payment_method`, `message_template`,
`customer`, `seller_notification_setting` and `telegram_update` are ownership
roots that either have no parent or have a nullable parent. Translation tables,
`product_action`, `inquiry`, `inquiry_message` and
`seller_notification_delivery` inherit a non-null parent chain and are left
unchanged.

`language` remains a global reference table. `bot_setting.store_id` makes the
default language store-specific. A per-store enabled-language set is a later
additive mapping (`store_language`); it is not needed by any current runtime
path and is deliberately not introduced in this compatibility migration.

## 3. Migration 0006 rules

`drizzle/0006_tenant_ownership_expansion.sql`:

- adds nullable `uuid` columns only;
- adds `REFERENCES store(id) ON DELETE RESTRICT` foreign keys;
- adds non-unique `store_id` indexes;
- does not add, drop or replace any unique constraint or index;
- does not insert, update, delete, truncate or seed any row;
- does not enforce composite ownership foreign keys yet;
- does not make any new column `NOT NULL`.

## 4. Runtime compatibility

The deployed single-store application keeps working because:

1. Every existing insert omits `store_id`, so PostgreSQL writes `NULL`.
2. Every existing read selects explicit columns or `*`; extra nullable columns do
   not change query shape or results.
3. The legacy unique constraints remain exactly in force, so duplicate slugs,
   Telegram ids, references and template keys are still rejected.
4. No runtime path filters by `store_id`, so no existing row becomes invisible.
5. The new foreign keys accept `NULL`; they only reject a non-null id that does
   not exist in `store`.

Nullable columns alone do **not** provide isolation. The application remains
single-store and must not claim tenant safety until the backfill, tenant-scoped
reads/writes and final composite constraints are separately approved.

### 4.1 Write paths that create `NULL` ownership before backfill

| Write path | Current behaviour |
| --- | --- |
| `src/lib/data/catalog.ts` category/product inserts | no `store_id` |
| `src/lib/data/actions.ts` product-action inserts | no `store_id` (derived) |
| `src/lib/data/payment-methods.ts` payment-method inserts | no `store_id` |
| `src/lib/data/templates.ts` message-template inserts | no `store_id` |
| `src/lib/data/customer.ts` `upsertCustomer` | no `store_id` |
| `src/lib/data/inquiry.ts` inquiry/inquiry-message inserts | no `store_id` |
| `src/lib/data/settings.ts` settings initialization | no `store_id` |
| `src/lib/data/seller-notifications.ts` setting writes | no `store_id` |
| `src/lib/data/telegram.ts` `claimTelegramUpdate` | no `store_id` |

This is intentional for S1.2: the compatibility deployment writes `NULL` until
the approved backfill assigns the legacy store. It is not isolation.

## 5. Legacy-store backfill plan — NOT EXECUTED

Artifacts:

- `docs/backfill/legacy-store-backfill.sql` — forward, idempotent plan.
- `docs/backfill/legacy-store-verification.sql` — read-only verification.

Execution is a separate operational approval after `0006` is applied. It is not
wired into any script, workflow, build or deployment.

### 5.1 Atomic execution contract

`legacy-store-backfill.sql` is exactly one `DO` statement. PostgreSQL executes
that statement atomically: store creation, every ownership update, the trigger
state changes and every validation either commit together or roll back
together. A failure after partial writes cannot leave partial ownership behind.

Supported execution:

```bash
psql "$DATABASE_URL" -v ON_ERROR_STOP=1 -f docs/backfill/legacy-store-backfill.sql
```

`psql -1` is also safe because the file is already one statement. Unsupported
execution methods are: splitting the file on semicolons, running selected
statements, autocommitting the DO body piece by piece, or invoking the file
from a migration runner, build, startup hook or deployment. Any client that
sends the complete file as one SQL command is supported; a client that
decomposes it is not.

The operator role must be able to `LOCK TABLE` and to disable/enable the
`*_touch_updated_at` triggers on the participating tables (table owner or
equivalent privilege). Insufficient privilege aborts the transaction before
any ownership change is committed.

### 5.2 Bounded write window and ordering

The DO statement sets `lock_timeout = 10s` and takes `ACCESS EXCLUSIVE` locks on
every participating table before taking its baseline snapshot. Legacy writes
therefore block for the duration of the transaction; a lock timeout aborts with
no change. No maintenance-mode framework is introduced.

Operational order:

1. Choose and record the approved window.
2. Quiesce legacy writes, or accept that they block while the backfill runs.
3. Run the atomic backfill.
4. Run `legacy-store-verification.sql` read-only and record every assertion and
   metric.
5. Only then resume writes under the chosen policy below.

### 5.3 Concurrent legacy writes — point-in-time only

The backfill cancels no writes and changes no runtime code. After commit, the
still-deployed legacy application can insert new rows with `store_id = NULL`.
That means:

- **Backfill succeeded** means every legacy row present during the locked
  transaction is owned by the legacy store at that point in time.
- **All future writes are tenant-owned** is **not** true in S1.2.

Two safe operational policies exist:

1. **Preferred completeness window:** keep legacy write paths quiesced after
   the backfill and deploy the S1.3 tenant-aware write path before resuming.
2. **Point-in-time window:** if S1.3 is not ready, run during a low-traffic
   window, keep writes blocked only for the backfill transaction, verify, then
   resume while explicitly recording that new rows may be unowned. A
   reconciliation backfill is required before any tenant-isolation claim.

No tenant-isolation claim may be made while NULL-ownership writes remain
possible. Continuous ownership completeness is an S1.3 runtime responsibility.

### 5.4 Preflight and postflight

Before writing, the backfill verifies:

- migration ledger exists with at least seven migrations (`0000`–`0006`);
- every required table and all eight direct `store_id` columns exist;
- the deterministic legacy store has exactly the expected name, slug and
  active status, or is created only when the store table is empty;
- no unrelated store exists;
- no row in any of the eight direct ownership tables is already owned by
  another store.

After writing, it verifies:

- all eight direct tables have no NULL and no wrong-store ownership;
- exactly one legacy store exists with the expected identity;
- category parent, product/category, inquiry/customer, inquiry/product,
  inquiry-message/thread and notification-delivery/thread relationships are
  consistent;
- a pre-write JSON baseline of row counts, relationship checksums, translation
  counts, notification states, Telegram update identities, activation flags
  and `updated_at` timestamps is byte-identical to the postflight baseline;
- the shared `updated_at` triggers are disabled only for the ownership updates
  and re-enabled before commit, so historical timestamps are preserved.

`legacy-store-verification.sql` is one read-only SELECT. Its `assertion` rows
must all have `ok = true`; its `metric` rows are audit evidence. SQL exit code
zero alone is not acceptance.

## 6. Rollback boundary

Before backfill: dropping the 0006 indexes, foreign keys and columns is a safe
code/schema rollback because all values are `NULL`.

After backfill: dropping the ownership columns is destructive and requires a
separate approved rollback plan with a verified restore point. The recommended
rollback is application rollback while keeping the additive schema, because the
old application ignores `store_id`.
