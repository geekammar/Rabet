# S1.2 — Tenant ownership expansion

**Scope:** additive schema preparation only. The application remains single-store
until a separately approved backfill (not executed here) and a later enforcement
phase. No additional store, merchant or membership is activated by this change.

## 1. Baseline

- Repository baseline: `main` at the merge of S1.1
  (`0005_tenant_identity_foundation` applied by the reviewed chain).
- S1.1 identity tables: `store`, `app_user`, `store_membership`.
- Existing application tables remain the operational schema. Migration `0006`
  only adds nullable `store_id` columns, foreign keys and non-unique indexes.

## 2. Ownership matrix

`PK` is the primary key, `Parent` is the row that determines ownership when no
direct column is added.

| Table | PK | Parent ownership | Direct `store_id` | Existing unique constraints | Existing FKs | Parent-derived sufficient | Future composite FK |
| --- | --- | --- | --- | --- | --- | --- | --- |
| `store` | `id` | root tenant | n/a (is the store) | `store_slug_unique` | none | n/a | none |
| `app_user` | `id` | global identity | no | `app_user_email_lower_unique` | none | yes; a user may join many stores | none |
| `store_membership` | `id` | `store`, `app_user` | already `store_id` | `store_membership_store_user_unique` | store, user | no; explicit link | none |
| `language` | `id` | global reference data | no | `language_code_unique` | none | yes; shared reference | future `store_language` mapping, not an FK |

| `category` | `id` | `category.parent_id` tree | **yes** | `category_slug_unique`; sibling/root order indexes | self parent | no; root categories have no parent | `(store_id, parent_id) -> category(store_id, id)` |

### 2.1 Why these ten roots get a direct column

`bot_setting`, `category`, `product`, `payment_method`, `message_template`,
`customer`, `inquiry`, `seller_notification_setting` and `telegram_update` are
ownership roots or aggregates that either have no parent, have a nullable
parent, or must be queried directly by the trusted store context. Translation
tables, `product_action`, `inquiry_message` and
`seller_notification_delivery` inherit a non-null parent chain and are left
unchanged.

`language` remains a global reference table. `bot_setting.store_id` makes the
default language store-specific. A per-store enabled-language set is a later
additive mapping (`store_language`); it is not needed by any current runtime
path and is deliberately not introduced in this compatibility migration.

## 3. Migration 0006 rules

`drizzle/0006_tenant_ownership_expansion.sql`:

- adds nullable `uuid` columns only;
- adds `REFERENCES store(id) ON DELETE RESTRICT` foreign keys;
- adds non-unique `store_id` indexes;
- does not add, drop or replace any unique constraint or index;
- does not insert, update, delete, truncate or seed any row;
- does not enforce composite ownership foreign keys yet;
- does not make any new column `NOT NULL`.

## 4. Runtime compatibility

The deployed single-store application keeps working because:

1. Every existing insert omits `store_id`, so PostgreSQL writes `NULL`.
2. Every existing read selects explicit columns or `*`; extra nullable columns do
   not change query shape or results.
3. The legacy unique constraints remain exactly in force, so duplicate slugs,
   Telegram ids, references and template keys are still rejected.
4. No runtime path filters by `store_id`, so no existing row becomes invisible.
5. The new foreign keys accept `NULL`; they only reject a non-null id that does
   not exist in `store`.

Nullable columns alone do **not** provide isolation. The application remains
single-store and must not claim tenant safety until the backfill, tenant-scoped
reads/writes and final composite constraints are separately approved.

### 4.1 Write paths that create `NULL` ownership before backfill

| Write path | Current behaviour |
| --- | --- |
| `src/lib/data/catalog.ts` category/product inserts | no `store_id` |
| `src/lib/data/actions.ts` product-action inserts | no `store_id` (derived) |
| `src/lib/data/payment-methods.ts` payment-method inserts | no `store_id` |
| `src/lib/data/templates.ts` message-template inserts | no `store_id` |
| `src/lib/data/customer.ts` `upsertCustomer` | no `store_id` |
| `src/lib/data/inquiry.ts` inquiry/inquiry-message inserts | no `store_id` |
| `src/lib/data/settings.ts` settings initialization | no `store_id` |
| `src/lib/data/seller-notifications.ts` setting writes | no `store_id` |
| `src/lib/data/telegram.ts` `claimTelegramUpdate` | no `store_id` |

This is intentional for S1.2: the compatibility deployment writes `NULL` until
the approved backfill assigns the legacy store. It is not isolation.

## 5. Legacy-store backfill plan — NOT EXECUTED

Artifacts:

- `docs/backfill/legacy-store-backfill.sql` — forward, idempotent plan.
- `docs/backfill/legacy-store-verification.sql` — read-only verification.

Execution is a separate operational approval after `0006` is applied. It is not
wired into any script, workflow, build or deployment.

1. Insert the deterministic store slug `legacy-store` with
   `ON CONFLICT (slug) DO NOTHING`; select the existing row on a retry.
2. Abort if any other store row exists, so two merchant stores are never merged.
3. Set `store_id` only where it is `NULL` in dependency order:
   `category`, `product`, `payment_method`, `message_template`, `customer`,
   `inquiry`, `seller_notification_setting`, `bot_setting`, `telegram_update`.
4. Do not update translations, actions, inquiry messages or notification
   deliveries; they inherit ownership from their unchanged parents.
5. Abort if any ownership row remains `NULL`.
6. Run the read-only verification queries and record the result.

This preserves category/product parent links, inquiry/customer identity,
notification outbox states, Telegram update idempotency, translated content,
message templates and demo activation flags. It invokes no Telegram API and
sends no notification.

## 6. Rollback boundary

Before backfill: dropping the 0006 indexes, foreign keys and columns is a safe
code/schema rollback because all values are `NULL`.

After backfill: dropping the ownership columns is destructive and requires a
separate approved rollback plan with a verified restore point. The recommended
rollback is application rollback while keeping the additive schema, because the
old application ignores `store_id`.
