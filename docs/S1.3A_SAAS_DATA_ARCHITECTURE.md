# S1.3-A — SaaS-native data architecture and legacy ownership rewrite

**Status:** implemented on `feat/saas-s1-3a-data-foundation`; unmerged and not
deployed. Migration `0006_tenant_ownership_expansion` is applied in Production;
the legacy-store backfill is **not executed**. No Production data, credential or
deployment was changed by this work.

This document records the data-layer boundary after S1.3-A. The application is
still one store, one Telegram bot and one administrator at runtime. The change
is that every store-owned write now resolves a trusted ownership context and
stamps new rows with the verified legacy store when it exists. Read isolation
is deliberately **not** switched on in this phase.

---

## 1. Product decision: one merchant, one store

The MVP will have multiple independent merchants on one platform, and **exactly
one manageable store per merchant account**. The schema keeps
`store_membership` as-is because its many-to-many shape is acceptable for the
identity foundation, but no MVP screen or service offers store switching,
multiple membership management, an agency dashboard, team roles or public
signup.

One Telegram bot per store and merchant onboarding arrive in later phases. This
phase does not activate a second store and does not optimize for multi-bot
runtime.

---

## 2. Old data-layer assumptions

Before S1.3-A the data layer assumed that:

- the first/only `bot_setting` row and the first/only
  `seller_notification_setting` row describe the whole deployment;
- a Telegram customer is globally unique by `telegram_id`;
- a Telegram update is globally unique by `update_id`;
- category, product, payment method, template, customer and update inserts
  omit `store_id`;
- an inquiry inherits ownership implicitly from its customer and a product is
  referenced without checking ownership;
- an administrator opening a dashboard is implicitly the owner of every row;
- process-global state does not identify a tenant, because there was only one.

Those assumptions are now explicit compatibility assumptions, not architecture.

---

## 3. Target architecture

```text
Trusted store context
        ↓
Store-aware business service
        ↓
Explicit data access (PostgreSQL, explicit projections, explicit batches)
        ↓
Shared PostgreSQL
```

Rules applied in this phase:

1. A store id is never read from a browser form, URL, Telegram payload or
   caller-provided argument.
2. The only trusted source is `resolveLegacyStoreContext(db)`.
3. No store is inferred with `LIMIT 1`; the resolver reads every store row.
4. No process-global selected store and no long-lived ownership cache exists.
5. No first user, first bot, first product or first row is treated as current.
6. Writes fail closed when the store identity is wrong or ambiguous.
7. Historical rows with `store_id IS NULL` remain valid until the approved
   backfill.
8. Read filtering is not activated yet; no old record is hidden.

---

## 4. Trusted legacy store contract

`src/lib/data/store-context.ts` is the only resolver:

- canonical identity: `slug = legacy-store`, `name = Rabet Legacy Store`,
  `status = active`;
- `missing`: no store row. New writes remain `NULL` for compatibility.
- `resolved`: exactly one store with the full canonical identity. New writes
  receive its id.
- invalid: wrong identity **or more than one store**. Every store-owned write
  throws `TENANT_CONTEXT_INVALID` before writing.
- the resolver never creates, updates or deletes a store;
- it performs one explicit PostgreSQL read and no network request;
- it is testable against isolated PostgreSQL.

Relationship helpers in the same module implement the temporary rule: a NULL
side is unresolved historical ownership; two non-NULL sides must match.
Incompatible writes throw `CROSS_STORE_REFERENCE`.

---

## 5. Ownership write coverage

The eight direct ownership roots are covered:

| Table | New row | Update / upsert |
| --- | --- | --- |
| `bot_setting` | `initializeSettings` stamps resolved id or NULL | updates never change `store_id` |
| `category` | `createCatalogCategory` stamps | edits preserve; parent/store compatibility checked |
| `product` | `createCatalogProduct` stamps | edits preserve; category/store compatibility checked |
| `payment_method` | `createPaymentMethod` stamps | edits preserve |
| `message_template` | `createTemplate` stamps | description/translation updates preserve |
| `customer` | `upsertCustomer` stamps | conflict update never sets `store_id` |
| `seller_notification_setting` | both insert paths stamp | conflict update never sets `store_id` |
| `telegram_update` | `claimTelegramUpdate` stamps | claim/processed/failed/receipt updates preserve |

Derived rows remain derived:

- `inquiry` ownership comes from its customer;
- an inquiry product must be ownership-compatible with the customer;
- `inquiry_message` derives from the inquiry;
- `seller_notification_delivery` derives from the inquiry;
- translations derive from their category, product, template or payment method;
- `product_action` derives from its immutable `product_id`;
- navigation and payment-method targets are checked against the owning product's
  store when both sides are already owned.

NULL compatibility is **temporary**. Runtime code never backfills an existing
row; a pre-existing NULL row remains NULL during updates until the approved
backfill.

No activation flag, admin credential, Telegram token, notification state or
delivery state is changed by ownership stamping.

## 6. Module inventory

| Module | Responsibility | Write entry points | Notes |
| --- | --- | --- | --- |
| `catalog.ts` | category/product read and write, translations, catalog transactions | create/edit/update category and product; translation saves | large module intentionally kept together; ownership checks added at catalog boundaries |
| `actions.ts` | product action tree and target validation | create/edit action | derived ownership through product; target ownership validated |
| `customer.ts` | Telegram identity and language/block state | upsert, selected language, blocked status | global `telegram_id` unique remains for the single-store transition |
| `inquiry.ts` | product/support inquiry creation, text routing, inbound messages | create/resume, append, route | raw CTE batches preserved; ownership preflight added; inquiry row remains derived |
| `seller-inbox.ts` | seller-side inquiry reads and reply delivery state | message delivery updates | derived through inquiry; no direct ownership columns |
| `settings.ts` | singleton bot configuration and storefront menu | initialize, update, menu save/reset | singleton constraints unchanged |
| `payment-methods.ts` | payment method configuration | create/edit/toggle | direct root; ownership preserved on edit |
| `templates.ts` | message templates and translations | create/update/save translation | direct root plus derived translations |
| `seller-notifications.ts` | notification setting and durable outbox | config save, verification, enabled toggle, cooldown, delivery state | direct setting root; outbox derived from inquiry |
| `telegram.ts` | update claim, lease, completion, receipt | claim and completion updates | direct root; update-id idempotency unchanged |

Read entry points remain the existing public functions. No generic repository,
reflection layer or dependency-injection framework was introduced.

### 6.1 Transaction boundaries

- Neon HTTP still has no interactive transaction; multi-statement writes use
  the existing `executeAtomicBatch` (`db.batch` on Neon, transaction on the
  PostgreSQL test driver).
- Inquiry/update fencing remains inside the existing atomic CTE batches.
- Ownership resolution is a separate explicit read before the write batch. The
  store is operator-provisioned, never created by runtime code; a provisioning
  race is therefore a documented cutover condition, not a self-healing path.
- No new lock or transaction was added around settings, catalog or Telegram
  writes.

### 6.2 Existing idempotency preserved

- customer: unique `telegram_id` + upsert;
- Telegram: unique `update_id`, claim/lease/fencing and attempt-scoped updates;
- inquiry: partial unique active-inquiry index and message-level unique index;
- templates: unique key and translation unique index;
- settings: singleton primary keys/checks;
- notification outbox: `(event_type, inquiry_id)` and reference uniqueness.

Ownership stamping does not create a second idempotency mechanism.

### 6.3 Cross-store risk review

- Direct-root inserts are stamped from the trusted resolver.
- Direct-root updates never transfer ownership.
- Product/category relation is checked on create and move.
- Inquiry/customer/product relation is checked before inquiry creation.
- Navigation/payment-method targets are checked against their product.
- Historical NULL sides are tolerated; this is documented, not hidden.
- A second store makes the legacy resolver fail closed, so the transitional
  runtime cannot silently choose one.
- Fragile whole-row catalog and payment-method reads were replaced with explicit
  projections. Inquiry raw SQL continues to project explicit columns and keeps
  its existing column shape; it was not rewritten.
- Full read authorization/isolation and global uniqueness replacement belong to
  S1.3-B.

### 6.4 Public API compatibility

All existing exported function names and inputs remain. `readSettings` now
returns the real `storeId` instead of a synthetic `null`; `PaymentMethodRecord`
exposes an optional `storeId`. No route, Server Action, webhook contract or
dashboard prop changed.

---

## 7. Preserved, adapted and rewritten

### Preserved

- All catalog, customer, inquiry, settings, payment-method, template,
  notification and Telegram business behaviour.
- Singleton constraints, unique constraints, activation flags, inquiry statuses,
  delivery states, snapshots and message idempotency.
- Existing raw CTE inquiry/routing batches and the webhook/token architecture.
- Existing tests; one S1.2 test was updated because the S1.3-A write path closes
  its intentionally documented NULL-write gap.

### Adapted

- Every direct-root insert now resolves the trusted store first.
- Upserts and updates omit `store_id`, so existing ownership is preserved.
- Catalog and inquiry writes validate parent/customer/product ownership.
- Product-action targets are validated against their store.
- Settings reads expose real ownership instead of assuming NULL.
- Catalog/payment-method reads use explicit projections.

### Rewritten

- None of the large business modules was replaced. The only new module is the
  small server-only store-context resolver. This is deliberate: a full
  `catalog.ts` or `inquiry.ts` rewrite would exceed S1.3-A and could not be
  validated safely in one PR.

---

## 8. Read-side position (S1.3-A only)

- Historical NULL rows remain visible: no read query filters by `store_id`.
- No store id from a caller authorizes a read.
- Catalog and payment-method reads use explicit projections where the old
  whole-row shape was fragile.
- The dashboard still has one administrator and one implicit store.
- **Read isolation is not complete and is not claimed.** S1.3-B must introduce
  trusted merchant authentication, store-scoped read contracts and enforcement
  over every read path, then replace transitional global uniqueness where
  required.

---

## 9. Telegram boundary

S1.3-A does not rebuild the Telegram runtime.

Preserved now:

- the existing webhook route and secret verification;
- the existing bot token and seller notification token sources;
- update idempotency, leases and completion fencing;
- webhook response codes and diagnostics;
- customer/inquiry/notification behaviour.

Future boundary (not implemented here):

- verified bot connection identity;
- connection-to-store mapping;
- updates claimed and processed only in a store scope;
- customer identity unique per store rather than globally;
- inquiry and notification routing scoped to the mapped store;
- multi-bot orchestration, planned for S5.

`telegram_update.store_id` is stamped now, so a future connection mapper can
audit transitional updates without changing the update idempotency key.

---

## 10. Settings and future replacements

The legacy singleton rows remain operational and their constraints remain in
place:

- `bot_setting` is still one row with `id = 1`;
- `seller_notification_setting` is still one row with `id = 1`;
- enabled languages remain the global `language.is_enabled` set.

Future replacement boundary:

- per-store bot configuration keyed by store;
- per-store seller notification configuration keyed by store;
- an additive `store_language` mapping for enabled languages;
- merchant-scoped settings screens.

No new settings table, multi-store settings UI or schema expansion is introduced
in this PR.

## 11. Safe cutover prerequisites (NOT EXECUTED)

The production order is:

1. **Deploy the compatible ownership-aware writes.** New rows are stamped when
   the legacy store exists and remain NULL when it does not.
2. **Drain or account for in-flight legacy requests.** Requests that resolved a
   missing store may complete with NULL ownership. Record the window; do not
   pretend the cutover is atomic.
3. **Run the approved backfill** from `docs/backfill/legacy-store-backfill.sql`
   in one atomic `DO` statement during the approved window, after quiescing or
   accepting blocked legacy writes.
4. **Verify zero unowned rows** with
   `docs/backfill/legacy-store-verification.sql`; all assertion rows must be
   `ok = true`. A zero SQL exit code alone is not acceptance.
5. **Run a reconciliation backfill** for any request that started before
   provisioning and completed with NULL after the first backfill.
6. **Enable final ownership enforcement only in a later phase.** Composite
   ownership foreign keys, `NOT NULL` ownership, per-store uniqueness and
   tenant-scoped reads belong to S1.3-B or later.

S1.3-A does not execute any of these steps. The only permitted runtime effect is
stamping new rows during normal application writes.

---

## 12. Deferred work and release gates

Deferred to S1.3-B and later:

- merchant authentication, invitations and onboarding;
- one-merchant-one-store membership enforcement in application flows;
- store-scoped read authorization across dashboard and webhook paths;
- replacement of global unique keys where per-store identity is required;
- composite ownership foreign keys and final `NOT NULL` enforcement;
- full store settings and language mapping tables;
- multi-bot connection identity and routing.

Release gate: this PR is a data-foundation change and must not be treated as
tenant isolation. Until S1.3-B and the approved backfill/reconciliation are
complete, no multi-merchant or multi-store runtime may be enabled.
